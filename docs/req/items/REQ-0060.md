> we should report gain every time we run solve exams, we should have metrics (standard metrics), actually we now solve with many failure, but later then we imrove and I want to see progress when we change something and have better exams solutions, how to count it, how to have it stats, and have script to cover it.

## Requirement
WHEN a solve run finishes, the system SHALL write a metrics summary (counts and rates computed from result.json, run.log and, when a key/QA/review exists, agreement with it) and append it to a per-exam run history; a script SHALL list runs and compare two runs (delta per metric, per subject, per question: fixed / regressed / unchanged) together with what changed between them (engine commit, prompt version, model, config).


## Acceptance
<!-- Each item objectively verifiable. VERIFIED requires every box ticked. -->
- [x] AC1: standard metrics defined and documented with exact formulas: answered / declined / uncertain / malformed rates, retry and QA-flip rates, agreement with key or QA line (accuracy when a key exists), needs_review count, calls, tokens, cost, time; per subject and per group kind (REQ-0058)
- [x] AC2: each run appends one JSON line to a history file (run id, time, exam id, git commit, prompt version, model, config, metrics); old runs without metrics are backfilled from their result.json
- [x] AC3: script subcommand compare shows two runs side by side with deltas and the list of questions that changed status or answer (fixed / regressed), and a trend view across runs
- [x] AC4: the solve run prints a short metrics block at the end and the report includes it; no paid call is needed to compute or compare metrics
- [x] AC5: tests-first on fixture result.json files; independent recount of the numbers (crosscheck) on one real DGNL run
